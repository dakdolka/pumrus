# Изменения теории по коду

## Как работать

1. В форме открыть **Теория → нужная тема → Изменения по коду**.
2. Нажать **Экспорт темы**. Файл содержит текущую опубликованную страницу со всеми блоками, вложенностью и авторскими пометками. Передать его для подготовки правок.
3. Вставить возвращённый JSON в поле **Код изменений**. Две страницы ниже покажут исходную и изменённую версии через обычный компонент теории, с тем же Markdown, таблицами, раскрывающимися группами и оформлением.
4. Изменять код в `after` или нажать на блок страницы **После** и воспользоваться обычным редактором блока. Правки редактора автоматически попадают в JSON. Кнопка **Перейти к after** прокручивает код к изменяемой части.
5. Нажать **Применить изменения**. Это публикация: создаётся новая версия темы, предыдущая сохраняется в истории. До нажатия содержимое темы на сервере не меняется.

На широком экране страницы стоят рядом, на телефоне — друг под другом. Каждую страницу можно прокручивать отдельно. **Скопировать код** сохраняет весь пакет для дальнейшей работы.

## Первый пример: омонимичные корни

У темы **«Чередующиеся корни»** задания 9 есть кнопка **Пример: Омонимичные корни · задание 9**. Она экспортирует текущую тему и применяет к её копии подготовленное ранее дополнение. Это тот же алгоритм, что в `app.scripts.task9_homonymy`, без записи в БД.

В `after` добавляются предупреждение об омонимии, сравнение «загорать / горевать / гористый» и четыре раскрывающихся подраздела. Существующие тексты, таблицы, заметки и вложенные блоки остаются. Если заголовки исходной темы изменены и дополнение нельзя однозначно расположить, показывается ошибка; исходник не подменяется текстом из репозитория.

Отдельный скрипт публикации для этого примера запускать не требуется. Пример привязан к реальной выгрузке выбранной темы, а не к демонстрационным идентификаторам.

## Формат пакета

Обычный JSON, без исполняемого кода. Также принимается JSON внутри блока ` ```json ` из ответа в чате.

| Поле | Назначение |
| --- | --- |
| `format` | Всегда `"pumrus.theory-edit"` |
| `schemaVersion` | Всегда `1` |
| `base` | Номер документа, исходной публикации и отпечаток содержимого; брать из экспорта и не менять |
| `before` | Исходная страница; не менять |
| `after` | Полная новая страница; редактировать её |

Страница содержит `title` (название документа), `ownerTitle` (название темы), `description` и `blocks`. Порядок блоков в массиве задаёт порядок показа. Вложенность задаётся через `children`, без ручных родительских ID.

Пример **одного блока внутри `after.blocks`**, не всего пакета:

```json
{
  "type": "section",
  "data": { "title": "Значения корней и омонимы" },
  "children": [
    {
      "type": "callout",
      "data": {
        "variant": "important",
        "markdown": "**Сначала установите значение корня.** Затем выбирайте правило."
      }
    },
    {
      "type": "table",
      "data": {
        "rows": [
          { "cells": ["Слово", "Как выбрать гласную"] },
          { "cells": ["Загорать", "Чередование **гар/гор**"] },
          { "cells": ["Горевать", "Проверка: **го́ре**"] }
        ]
      }
    }
  ]
}
```

`id` существующего блока сохранять. Новому блоку можно не задавать `id`; форма и сервер присвоят ему внутренний идентификатор. Одинаковые `id` запрещены. Для удаления блока удалить его объект из `after`; удаление группы удалит её `children`. Для перемещения перенести объект в нужное место массива, сохранив его `id`.

Поддерживаемые `type`: `rich_text`, `section`, `callout`, `example`, `list`, `table`, `image`, `video_embed`, `practice_link`, `theory_link`. Поля `data` и `settings` совпадают с обычными блоками формы. Варианты выносок: `rule`, `warning`, `important`, `note`, `tip`. Для заголовка текстового блока используется `settings.variant: "heading_2"` или `"heading_1"`.

### Переход к продолжению темы

В форме тип **«Продолжение теории»** позволяет выбрать тему из каталога и изменить текст карточки и кнопки. Чтобы открыть конкретное правило, задайте у целевого блока **«Метка для ссылки»**, а в карточке — ту же метку в поле **«Раздел в теме»**. Метка сохраняется между публикациями, даже когда внутренние ID блоков меняются. Допустимы 1–64 строчные латинские буквы, цифры и дефис; первый символ — буква. В одной теме метки уникальны.

```json
{
  "type": "theory_link",
  "data": {
    "taskNumber": 11,
    "topicId": 19,
    "anchor": "i-y-suffix",
    "markdown": "**Продолжим правило:** И/Ы в суффиксах прилагательных.",
    "buttonLabel": "Продолжить тему в задании 11"
  }
}
```

У целевого блока: `"settings": {"anchor": "i-y-suffix"}`. Поле `data.anchor` необязательно: без него открывается начало темы. Ссылка ведёт на `/theory/tasks/11/topics/19#theory-i-y-suffix`; целевой раздел и его родительские группы автоматически раскрываются. В предпросмотре формы ссылка выбирает блок для правки. На странице ученика она открывает продолжение; доступно также обычное открытие в новой вкладке.

Для изменения нескольких тем готовится отдельный пакет на каждую. Пакеты используют актуальные экспорты своих документов. Например, `app.scripts.split_task9_suffix_rules` готовит шесть пакетов И/Ы и О/Е/Ё для заданий 9 и 11 из шести выгрузок API, не подключаясь к БД. Сначала примените пакеты задания 11, затем задания 9, чтобы новые продолжения уже были доступны по ссылкам.

В Markdown: `**жирный**`, `*курсив*`, ссылки `[текст](https://...)`; перенос строки внутри JSON-строки записывается как `\n`. В списке пункты задаются `data.items: ["Первый", "Второй"]`, вид — `data.style: "ordered"` или `"unordered"`.

Неизвестные поля в структуре страницы и блока отклоняются: это помогает обнаруживать опечатки. Максимум — 2000 блоков и 32 уровня вложенности; поле вставки принимает до 2 миллионов символов.

## Проверки при применении

- Пакет должен относиться к выбранному документу и его текущей опубликованной версии.
- Проверяется отпечаток всех исходных блоков и названий: правки в другой вкладке после экспорта не будут затёрты. При конфликте нужно заново экспортировать тему и перенести свои правки.
- `before` должен оставаться исходным. Ошибка JSON или неизвестный тип блокирует применение.
- Если обычный редактор содержит неопубликованные локальные изменения, применение недоступно. Сначала завершить их, затем экспортировать заново.
- При существующем серверном черновике применение отклоняется, чтобы не обходить чужую незавершённую работу.
- Пустая тема не публикуется. Нажатие без изменений не создаёт лишнюю версию.
- Создание версии выполняется обычным механизмом публикации в одной транзакции с блокировкой документа и владельца. До применения экспорт и предпросмотр ничего не записывают.

Пакет не содержит ключ доступа. Выгрузка и применение используют обычную авторизацию владельца формы.

## API

- `GET /api/v2/admin/theory-documents/{id}/edit-package` → `{package, examples}`.
- `GET /api/v2/admin/theory-documents/{id}/edit-package?example=task9-homonymy` → пакет дополнения на основе текущей темы задания 9.
- `POST /api/v2/admin/theory-documents/{id}/apply-package` с самим JSON-пакетом → обновлённый документ с новой опубликованной версией.

На сервер нужно доставить изменения backend и собрать frontend. Миграция схемы БД не требуется.

# UmRus — Architecture

## 1. Статус документа

Статус: **Architecture Baseline v0.5**.

Документ фиксирует согласованную целевую архитектуру Telegram WebApp UmRus и результаты аудита прототипа `dakdolka/pumrus`.

Архитектура считается достаточной для начала поэтапной реализации базового каркаса. Открытые вопросы перечислены отдельно и не должны блокировать части системы, для которых уже определены инварианты.

При расхождении реализации с этим документом необходимо:

1. либо привести реализацию в соответствие;
2. либо оформить архитектурное решение в ADR и обновить документ.

## 2. Контекст и цели продукта

UmRus — учебная платформа для подготовки к ЕГЭ по русскому языку.

В первой версии Telegram является основной точкой входа: пользователь взаимодействует с Telegram-ботом, а учебный интерфейс открывается как Telegram WebApp. Бот работает через webhook, а не через long polling.

В дальнейшем тот же продукт должен быть доступен как обычное браузерное приложение. Поэтому Telegram является первым клиентским каналом, но не частью идентичности предметной модели и не единственным способом аутентификации.

Продукт должен предоставлять:

- полную теорию по заданиям ЕГЭ;
- деление материала задания на небольшие темы;
- практику по заданию целиком и по отдельным темам;
- повторение допущенных ошибок;
- быстрый переход между связанной теорией и практикой;
- административный интерфейс для постоянного наполнения контентом.

Главная архитектурная цель — позволить расширять каталог, теоретические блоки и форматы упражнений без переработки ядра приложения.

Архитектура оптимизируется прежде всего под:

- качество и сопровождаемость контента;
- мобильный интерфейс Telegram;
- предсказуемую навигацию;
- корректное восстановление учебной сессии;
- серверную достоверность результатов;
- постепенное развитие без преждевременного перехода к микросервисам.

Архитектура также должна допускать:

- платный контент, подписки и отдельные покупки;
- предоставление доступа по тарифу, промокоду или административному назначению;
- браузерную авторизацию независимо от Telegram;
- интеграции с платёжными и другими сторонними API;
- приём и надёжную обработку внешних webhook-событий.

## 3. Границы MVP

В MVP входят:

- Telegram-аутентификация пользователя;
- Telegram-бот с webhook endpoint;
- каталог заданий ЕГЭ и тем;
- теория задания и темы;
- блочный рендеринг теории;
- практика задания и темы;
- повторение ошибок как режим практики;
- практические сессии с восстановлением;
- контекстное открытие практики из теории;
- контекстное открытие теории из практики;
- административное создание и редактирование контента;
- черновик, проверка и публикация контента;
- базовый журнал изменений;
- четыре формата взаимодействия:
  - `single_choice`;
  - `multiple_choice`;
  - `text_input`;
  - `stress_selection`.

За границами первого MVP:

- пробный экзамен;
- сложная адаптивная выдача;
- интервальные алгоритмы высокой точности;
- частичные баллы для составных заданий;
- произвольные пользовательские курсы;
- микросервисная архитектура;
- микрофронтенды;
- визуальный конструктор новых программных типов блоков или упражнений без разработки.

Полноценная монетизация и браузерный вход реализуются после учебного MVP. В первой версии закладываются только границы модулей и точки расширения; платёжный провайдер, checkout, подписки и платёжные webhook пока не реализуются.

## 4. Архитектурные принципы

### 4.1. Модульный монолит

Frontend и backend строятся как модульные монолиты с явными доменными границами. Микросервисы не используются до появления измеримой потребности в независимом масштабировании или развёртывании.

### 4.2. Одна предметная иерархия

Теория и практика имеют самостоятельные пользовательские входы, но используют общие сущности:

```text
CourseVersion → ExamTask → Topic
```

Отдельные копии заданий и тем для теории, практики и ошибок не создаются.

### 4.3. Сервер является источником истины

Backend:

- проверяет ответы;
- фиксирует версию упражнения;
- сохраняет попытки;
- управляет состоянием сессии;
- формирует очередь ошибок;
- определяет доступ к административным операциям.

Правильный ответ не передаётся клиенту до отправки попытки, кроме специального административного preview.

### 4.4. Версионирование изменяемого контента

Опубликованные теория и упражнения неизменяемы. Редактирование создаёт новую версию. Старые попытки продолжают ссылаться на ту версию упражнения, которая была показана пользователю.

### 4.5. Расширяемость через контракты и реестры

Новый экземпляр известного типа создаётся без изменения кода. Новый фундаментальный тип требует изолированного добавления:

- схемы данных;
- валидатора;
- frontend-рендерера или interaction-компонента;
- административного редактора;
- при необходимости серверной стратегии проверки;
- тестов и мигратора схемы.

Ядро движка при этом не изменяется.

### 4.6. URL и серверная сессия вместо скрытой навигации

Каноническое местоположение восстанавливается из URL. Временный контекст переключения режима и неотправленный ответ восстанавливаются из session state и состояния `PracticeSession`.

### 4.7. Клиентские каналы отделены от домена

Telegram WebApp и будущий браузерный сайт используют одно API и одну предметную модель. Telegram ID не является первичным идентификатором пользователя.

Внутренняя сущность `User` связывается с одной или несколькими внешними идентичностями:

```text
User
└── UserIdentity[]
    ├── telegram
    └── browser provider
```

### 4.8. Доступ отделён от контента

Платность не моделируется набором полей `is_paid` во всех таблицах. Контент связывается с политикой доступа, а право конкретного пользователя определяется модулем Entitlements.

Это позволяет поддерживать:

- бесплатный контент;
- подписку;
- разовую покупку;
- тарифные уровни;
- временный доступ;
- промокоды;
- административно выданный доступ.

### 4.9. Внешние интеграции изолированы адаптерами

Предметные модули не вызывают Telegram, платёжного провайдера или другой внешний API напрямую. Интеграции подключаются через порты и адаптеры, имеют таймауты, повторные попытки, идемпотентность и журнал операций.

## 5. Архитектурные инварианты

1. Breadcrumb содержит не более трёх элементов:

   ```text
   Раздел → Задание → Тема
   ```

2. Контекстный переключатель «Теория/Практика» не является частью breadcrumb.
3. Теория и практика не имеют независимых копий `ExamTask` и `Topic`.
4. Ошибки не являются отдельным каталогом упражнений.
5. Все режимы решения используют единый `PracticeSession`.
6. Все пользовательские ответы проверяются сервером.
7. `Attempt` является неизменяемым журналом фактов.
8. Опубликованная версия контента не редактируется на месте.
9. API не доверяет `user_id`, переданному клиентом; пользователь определяется из проверенной сессии.
10. Новый тип блока или упражнения не добавляется условием в один центральный компонент.
11. Клиент может восстановить активную тренировку после контекстного открытия теории и возврата.
12. Удаление опубликованного или использованного контента выполняется как архивирование, если физическое удаление нарушит историю.
13. Telegram webhook проверяется до запуска прикладного сценария и обрабатывается идемпотентно.
14. Telegram ID и идентификатор браузерного провайдера являются внешними идентичностями, а не `User.id`.
15. Решение о доступе к платному контенту принимается сервером через Entitlements.
16. Статус платежа изменяется только на основании подтверждённого серверного ответа или проверенного webhook провайдера.
17. Внешний сбой не должен оставлять локальную бизнес-операцию в неопределённом состоянии.

## 6. Пользовательские сценарии

### 6.1. Чтение теории

```text
Главная → Теория → Задание → Тема
```

Пользователь может читать вводную теорию задания или теорию конкретной темы.

### 6.2. Обычная практика

```text
Главная → Практика → По заданиям → Задание
Главная → Практика → По темам → Задание → Тема
```

После выбора области backend создаёт `PracticeSession` и фиксирует состав упражнений.

### 6.3. Практика из теории

```text
Теория → Задание → Тема      [Практика]
```

- breadcrumb остаётся теоретическим;
- открывается практика только текущего задания или темы;
- перехода в общий каталог практики нет;
- сохраняется позиция чтения;
- создаётся или восстанавливается отдельная `PracticeSession`;
- Telegram BackButton или повторное нажатие переключателя закрывает практику и возвращает теорию.

### 6.4. Теория из практики

```text
Практика → Задание → Тема      [Теория]
```

- breadcrumb остаётся практическим;
- открывается связанная теория текущего задания или темы;
- `PracticeSession` не уничтожается;
- сохраняются позиция упражнения и неотправленный ответ;
- после закрытия теории пользователь возвращается в прежнее состояние практики.

### 6.5. Повторение ошибок

```text
Главная → Практика → Повторение ошибок
```

Пользователь может ограничить очередь заданием или темой. Текущая ошибка предоставляет контекстный доступ к связанной теории без завершения сессии.

## 7. Информационная архитектура

### 7.1. Главная страница

На главной странице находятся:

- логотип UmRus;
- кнопка «Теория»;
- кнопка «Практика»;
- информационный блок о продукте.

### 7.2. Изменение информационной архитектуры

После анализа пользовательских сценариев принято решение отказаться от отдельного раздела **«Ошибки»** на главной странице.

Ошибки являются не самостоятельным способом обучения, а одним из режимов практики.

Пользователь приходит в раздел **«Практика»**, после чего выбирает источник упражнений:

- практика по заданиям;
- практика по темам;
- повторение ошибок;
- в будущем — пробный вариант.

Таким образом, все механики решения упражнений используют единый движок `PracticeSession` и отличаются способом формирования набора упражнений.

Раздел «Ошибки» представляет собой не отдельное хранилище заданий, а интерфейс к очереди повторения (`Mistake Queue`), сформированной на основании истории попыток пользователя.

В базе данных упражнения не дублируются. Состояние ошибки хранит ссылку на упражнение, данные повторения и ссылки на породившие его попытки.

Контекстная теория поддерживается и внутри режима повторения ошибок. Пользователь может открыть связанную теорию по текущей теме без выхода из `PracticeSession`, после чего продолжить решение с того же места.

## 8. Навигация и state machine

### 8.1. Канонические маршруты

```text
/
/theory
/theory/tasks/:taskId
/theory/tasks/:taskId/topics/:topicId

/practice
/practice/tasks/:taskId
/practice/tasks/:taskId/topics/:topicId
/practice/mistakes
/practice/sessions/:sessionId
```

Идентификаторы маршрута должны быть стабильными. Человекочитаемые slug могут добавляться, но не являются единственной идентичностью сущности.

### 8.2. Слои состояния

| Слой | Содержимое |
|---|---|
| URL state | раздел, задание, тема, идентификатор сессии |
| Server state | каталог, документы, опубликованные упражнения, прогресс |
| Practice state | состав сессии, позиция, отправленные ответы |
| Navigation context | исходный режим и контекстный overlay |
| Draft response | введённый, но не отправленный ответ |
| Local UI state | открытые панели, анимации, локальный фокус |

### 8.3. Контекстный overlay

Состояния:

```text
base
├── theory_overlay
└── practice_overlay
```

Допустимые переходы:

```text
TheoryBase   → PracticeOverlay → TheoryBase
PracticeBase → TheoryOverlay   → PracticeBase
MistakeMode  → TheoryOverlay   → MistakeMode
```

Overlay не изменяет корневой навигационный контекст и не предоставляет переход в каталог противоположного раздела.

### 8.4. Восстановление

Для практики сохраняются:

- `sessionId`;
- текущий `sessionItemId`;
- позиция;
- неотправленный ответ;
- открытый контекст теории;
- время последнего изменения.

Отправленные ответы не восстанавливаются из недоверенного локального снимка: они загружаются из backend.

## 9. Доменная модель

```text
Course
└── CourseVersion
    └── ExamTask
        ├── TheoryDocument
        ├── Topic[]
        │   └── TheoryDocument
        └── TaskDocument
            └── ExerciseSet references
```

### 9.1. Каталог

- `Course` — учебный продукт, например «ЕГЭ по русскому языку».
- `CourseVersion` — редакция курса для конкретной спецификации экзамена.
- `ExamTask` — задание экзамена, его номер, название и порядок.
- `Topic` — тема внутри задания.

Глубина тем в MVP ограничена одним уровнем внутри задания.

Тема может быть связана с несколькими заданиями через таблицу ассоциаций. При отображении тема всегда открывается в контексте конкретного задания, поэтому breadcrumb остаётся однозначным:

```text
Раздел → текущее задание → тема
```

Связь может содержать порядок темы внутри задания и признак основного задания для административного отображения.

### 9.2. Теория

```text
ExamTask
├── introductory TheoryDocument
└── Topic
    └── TheoryDocument
```

### 9.3. Практика

`TaskDocument` описывает организацию практической страницы:

```text
TaskDocument
├── introduction
├── configuration
├── task-level ExerciseSet references
└── topic-level ExerciseSet references
```

`TaskExercise` и `TopicExercise` не являются разными физическими моделями.

### 9.4. Упражнение

```text
Exercise
├── ExerciseVersion[]
├── ExamTask links
├── Topic links
└── ExerciseSet memberships
```

Одно упражнение может участвовать:

- в практике задания;
- в практике темы;
- в повторении ошибок;
- в диагностической подборке;
- в будущем пробном варианте.

### 9.5. Пользователь и внешние идентичности

```text
User
├── UserIdentity[]
├── Entitlement[]
└── PracticeSession[]
```

`UserIdentity` содержит тип провайдера, внешний идентификатор и проверенные метаданные связи. Такая модель позволяет позднее связать Telegram-аккаунт с браузерным входом, не создавая второго учебного профиля.

### 9.6. Коммерческий доступ

```text
Product
├── Price[]
└── AccessGrant[]

User
├── Purchase[]
├── Subscription[]
└── Entitlement[]

ProtectedResource
└── AccessPolicy
```

- `Product` — продаваемое предложение, например полный курс или тематический пакет.
- `Price` — цена, валюта, провайдер и период действия предложения.
- `Purchase` — разовая коммерческая операция.
- `Subscription` — возобновляемый доступ, если он поддерживается провайдером.
- `Entitlement` — фактическое право пользователя на ресурс или возможность.
- `AccessPolicy` — правило доступа к курсу, документу, подборке или функции.

`Purchase` и `Subscription` не заменяют `Entitlement`: платёж является причиной выдачи доступа, а entitlement — проверяемым результатом. Это также позволяет выдавать доступ без платежа.

## 10. Архитектура frontend

Рекомендуемый frontend — React + TypeScript в виде модульного монолита.

```text
app/
├── routing
├── telegram
├── auth
├── navigation
└── error-boundaries

features/
├── home
├── theory
├── practice
├── mistake-review
├── contextual-learning
└── admin

entities/
├── course
├── exam-task
├── topic
├── theory-document
├── exercise
└── practice-session

engines/
├── theory-block
└── exercise

shared/
├── api
├── ui
├── validation
└── utilities
```

Требования:

- маршруты не управляются строковым `page` в корневом компоненте;
- серверные данные не копируются без необходимости в глобальный store;
- контекстные overlay-режимы имеют отдельную state machine;
- каждый тип блока и interaction регистрируется через registry;
- административный интерфейс использует общие схемы, но отдельную точку входа и отдельную проверку прав;
- состояние активной практики не зависит от жизненного цикла одного React-компонента.

## 11. Архитектура backend

Backend строится как модульный монолит:

```text
Identity
Catalog
Content
ExerciseBank
Practice
Attempts
MistakeReview
Progress
AccessControl
Commerce
Integrations
Administration
Media
Audit
```

Внутри модуля:

```text
API → Application use case → Domain → Repository port → Infrastructure
```

Модули не обращаются напрямую к таблицам других модулей. Межмодульные операции выполняются через application services или явно определённые read-модели.

Одна транзакция должна атомарно:

1. проверить ответ;
2. сохранить `Attempt`;
3. обновить состояние элемента сессии;
4. создать или обновить активную ошибку;
5. обновить оперативный прогресс.

Тяжёлые аналитические агрегаты могут обновляться асинхронно.

### 11.1. Telegram Bot Gateway

Telegram Bot Gateway является входным адаптером backend.

Поток обновления:

```text
Telegram → HTTPS webhook → signature/secret validation
         → deduplication by update_id
         → command dispatcher
         → application use case
         → response through Telegram API adapter
```

Webhook endpoint должен быстро подтвердить приём. Долгие и повторяемые операции передаются фоновой очереди. Повторная доставка одного update не должна повторно создавать пользователя, платёж или другую бизнес-операцию.

### 11.2. Integrations

Модуль интеграций содержит адаптеры:

- Telegram Bot API;
- платёжных провайдеров;
- object storage;
- почты или уведомлений в будущем;
- аналитики и иных внешних сервисов.

Исходящие бизнес-события, требующие надёжной доставки, записываются в transactional outbox в той же транзакции, что и доменное изменение. Отдельный worker отправляет события и фиксирует результат.

Упражнение разделяется на независимые аспекты:

```text

```

### 15.1. Форматы MVP

#### `single_choice`

```text

```

#### `multiple_choice`

```text
response: optionId[]

```

#### `text_input`

```text

```

#### `stress_selection`

`stress_selection` является структурированным взаимодействием, а не вводом изменённой строки.

```yaml

  word: "звонит"
  selectablePositions: [2, 4]

  selectedCharacterIndex: 4

  type: exact_position
```

Хранится индекс выбранной позиции. Это устраняет неоднозначности регистра, Unicode, `ё`, повторяющихся гласных и разных способов записи знака ударения.

Backend registry отвечает за:

- валидацию response schema;
- нормализацию;
- выбор checker strategy;
- безопасную проверку;
- формирование результата.

## 16. Практические сессии

`PracticeSession` создаётся backend и содержит неизменяемый снимок набора упражнений.

Режим определяет только стратегию формирования набора, а не отдельный движок решения.

Состояния:

```text
created → active → completed
                 ↘ abandoned
                 ↘ expired
```

Сессия должна поддерживать идемпотентную отправку ответа с клиентским ключом запроса, чтобы повторный сетевой запрос не создавал две попытки.

Неотправленный ответ может временно храниться на клиенте. После отправки источником истины становится backend.

В MVP пользователь может иметь несколько исторических сессий, но только одну активную сессию для одной комбинации `mode + scope`. Явный выход из тренировки закрывает сессию. Контекстное открытие теории не считается выходом и не закрывает её.

Незавершённая сессия, из которой пользователь не вышел явно, истекает после конфигурируемого периода неактивности. Начальное значение — 24 часа; это эксплуатационная настройка, а не жёсткое доменное правило.

### 16.1. Частичная проверка

Результат попытки содержит:

```text
score
max_score
status: incorrect | partial | correct
component_results[]
feedback
theory_links[]
```

Визуальное состояние:

- `incorrect` — красное;
- `partial` — жёлтое;
- `correct` — зелёное.

Для составного упражнения checker возвращает результат по каждому проверяемому компоненту. Feedback после отправки обязательно содержит правильный ответ или правильные ответы и ссылки на связанную теорию. До отправки попытки эти данные клиенту не выдаются.

## 17. Ошибки и прогресс

Модель различает:

- `Attempt` — факт отправки ответа;
- неправильную попытку — `Attempt` с ошибочным результатом;
- `MistakeItem` — агрегированное состояние проблемы по упражнению;
- исправленную ошибку;
- повторно открытую ошибку.

Базовое правило MVP:

- первая неправильная попытка создаёт `active`;
- повторная ошибка обновляет счётчики и дату;
- ошибки доступны в `Практика → Ошибки`;
- список группируется по заданиям;
- пользователь может запустить все ошибки либо ошибки выбранного задания;
- из текущего упражнения можно открыть связанную теорию без закрытия сессии;
- правильное решение переводит ошибку в `removal_candidate`, но не удаляет её немедленно;
- после завершения блока появляется popup со списком правильно решённых ошибок;
- пользователь подтверждает, какие элементы убрать из активного списка;
- закреплённая ошибка остаётся активной, пока пользователь явно не снимет закрепление или не удалит её вручную;
- новая неправильная попытка по исправленному упражнению переводит его в `reopened`.

Таким образом, «исправлено автоматически» и «убрано пользователем из списка» являются разными событиями.

## 18. Административная панель

Административный интерфейс — отдельная точка входа с общей дизайн-системой и API-клиентом.

Полноценная ролевая редакционная модель в MVP не нужна. Остаются только два уровня доступа:

- `learner`;
- `administrator`.

Это минимальная граница безопасности, а не редакционный workflow. Администратор может редактировать и публиковать; обычный пользователь не имеет доступа к административным API.

Функции:

- управление курсом, заданиями и темами;
- блочный редактор теории;
- создание упражнений;
- выбор interaction и checker;
- preview мобильного интерфейса;
- валидация;
- изменение порядка;
- создание подборок;
- публикация и архивирование;
- аудит изменений.

Новый тип программного блока или interaction не создаётся администратором. Администратор создаёт экземпляры зарегистрированных типов.

## 19. Версионирование и публикация

Workflow MVP:

```text
draft → published → archived
```

Правила:

- опубликованная версия неизменяема;
- публикация атомарно переключает активную версию;
- черновик может создаваться из опубликованной версии;
- пользовательские запросы получают только опубликованные версии;
- preview может получать draft только администратор;
- попытка всегда ссылается на конкретную `ExerciseVersion`.

## 20. Telegram, browser authentication и безопасность

Frontend отправляет Telegram `initData` backend. Backend:

1. проверяет подпись по алгоритму Telegram;
2. проверяет срок действия данных;
3. извлекает Telegram user ID;
4. создаёт внутреннюю пользовательскую сессию;
5. не доверяет `initDataUnsafe` как доказательству личности.

Telegram-бот получает update только через HTTPS webhook. При настройке webhook используется секретный token или секретный путь, а endpoint дополнительно проверяет допустимые заголовки и ограничивает размер тела запроса.

Будущее браузерное приложение использует отдельный стандартный механизм входа. Предпочтительны OIDC/OAuth 2.1 через выбранного identity provider либо собственная серверная сессия с безопасной процедурой входа. Browser credentials не добавляются в Telegram-таблицу: они создают ещё один `UserIdentity`.

Связывание Telegram и browser identity требует подтверждения владения обеими идентичностями. Автоматическое объединение только по совпавшему имени, username или непроверенному email запрещено.

Bot API не позволяет произвольно получить Telegram-профиль по номеру телефона. В MVP профиль создаётся из проверенного Telegram `initData`. Телефон может использоваться только после явной передачи контакта пользователем и не рассматривается как основной способ будущей браузерной аутентификации.

Требования:

- пользователь не передаёт авторитетный `user_id` в бизнес-командах;
- административные endpoints защищены ролями;
- правильные ответы удалены из пользовательского payload вопроса;
- media upload проверяет MIME, размер и права;
- checker `regex` при появлении должен иметь ограничения от ReDoS;
- аудит фиксирует публикацию, архивирование и изменение ролей.

Для платёжных интеграций дополнительно:

- секреты хранятся во внешнем secret storage или переменных окружения;
- webhook-подпись проверяется по документации конкретного провайдера;
- создание checkout и обработка webhook идемпотентны;
- frontend не может самостоятельно подтвердить успешную оплату;
- журнал платежей и выдача entitlement выполняются транзакционно;
- персональные и платёжные данные минимизируются.

### 22.3. Теория

Фактические типы блоков:

- `title`;
- `subtitle`;
- `rule`;
- `example`;
- `exception`;
- `important`;
- `text`;
- `svg`;
- `group`;
- `link`;
- `note`.

Блок хранит `type`, строковый `content`, `order`, `parent_id` и дочерние блоки. Frontend рендерит типы центральным `switch`.

Полезные идеи:

- явный порядок;
- повторное использование теории;
- составной блок;
- отдельный редактор.

Не переносится один к одному:

- `title` и `subtitle` могут быть вариантами rich text;
- `rule`, `important` и `note` становятся вариантами callout;
- `group` требует ограниченного контракта вложенности;
- `svg` рассматривается как media/image-вариант;
- `link` обычно является частью rich text, а не отдельным блоком;
- строковый `content` заменяется типизированным `data`.

### 22.4. Практика

Фактические типы тренажёров:

- `options`;
- `input`;
- `stress`;
- `dictionary`.

Существуют:

- `TaskGroup`;
- `Task`;
- `TaskItem`;
- `Option`;
- `OptionSet`;
- `TaskSession`;
- `UserMistake`.

`UniversalTrainer` повторно используется для обычной практики и ошибок. Это решение сохраняется концептуально в виде единого Exercise Engine и `PracticeSession`.

Ограничения прототипа:

- правильные ответы передаются клиенту;
- проверка выполняется во frontend;
- `trainer_type` смешивает interaction и checker;
- серверная сессия не фиксирует набор и порядок упражнений;
- фактическое состояние сессии в значительной степени хранится в `localStorage`;
- ошибки являются отдельными записями неправильных ответов;
- каталоги теории и практики не связаны общей сущностью `ExamTask/Topic`.

### 22.5. Backend

Backend уже использует полезное направление:

```text
API → use case → repository interface → repository implementation
```

Это направление сохраняется, но модули перестраиваются вокруг целевых доменов.

### 22.6. Безопасность прототипа

Прототип использует `initDataUnsafe`, принимает пользовательские идентификаторы от клиента и предоставляет административные операции без достаточной видимой границы авторизации. Эти подходы не переносятся в целевую систему.

## 23. Стратегия миграции

Миграция выполняется через адаптеры, а не изменением старых записей на месте.

### Этап 1. Каталог

- создать `CourseVersion`, `ExamTask`, `Topic`;
- сопоставить существующие группы и задания;
- зафиксировать таблицу соответствий старых и новых ID.

### Этап 2. Теория

- преобразовать существующие блоки в новые типы;
- сохранить исходный идентификатор в migration metadata;
- валидировать каждый документ;
- вручную проверить неоднозначные `group`, `svg` и `link`.

### Этап 3. Практика

- преобразовать `Task/TaskItem` в `Exercise/ExerciseVersion`;
- преобразовать option sets в interaction config;
- вынести правильные ответы в закрытую checker-конфигурацию;
- сопоставить старые типы с MVP interactions.

### Этап 4. Пользовательские данные

- старые ошибки импортировать как исторические факты только при достаточной достоверности связей;
- не создавать искусственную точность прогресса из неполных данных;
- при необходимости начать новую Mistake Queue, сохранив старую историю отдельно.

## 25. Риски и компромиссы

### JSONB

Даёт расширяемость, но требует обязательных схем, версий и серверной валидации. JSONB без registry-контрактов запрещён.

### Overlay-навигация

Хорошо удерживает учебный контекст, но сложнее обычной маршрутизации. Поэтому переходы описываются state machine и покрываются сценарными тестами.

### Версионирование

Увеличивает количество таблиц и административных операций, но необходимо для достоверности попыток и безопасной публикации.

### Универсальный Exercise Engine

Не должен превращаться в один компонент со множеством условий. Общим остаётся жизненный цикл упражнения, а interaction и checker подключаются через реестры.

### Mistake Queue

Первое правило исправления неизбежно будет упрощённым. Модель должна позволять заменить алгоритм без изменения истории `Attempt`.

### Монетизация

Ранняя реализация всей платёжной системы замедлит учебный MVP. Компромисс: сразу выделить `AccessPolicy` и Entitlements как границу, но подключать конкретного провайдера отдельным этапом.

### Сторонние API

Повторные доставки, таймауты и временная недоступность являются нормой. Интеграции должны быть идемпотентными и наблюдаемыми; нельзя строить доменную транзакцию на предположении, что внешний вызов всегда успешен.

## 26. ADR

### ADR-001: модульный монолит

Принято: frontend и backend реализуются модульными монолитами.

### ADR-002: общая предметная иерархия

Принято: теория и практика имеют общие `ExamTask` и `Topic`, несмотря на самостоятельные входы в интерфейсе.

### ADR-003: ошибки как режим практики

Принято: отдельная кнопка «Ошибки» удаляется с главной. Повторение ошибок является режимом создания `PracticeSession`.

### ADR-004: контекстный переключатель

Принято: практика из теории и теория из практики открываются как ограниченный overlay. Переключатель не входит в breadcrumb.

### ADR-005: серверная проверка

Принято: клиент собирает типизированный ответ, backend выполняет нормализацию и проверку.

### ADR-006: версия упражнения в сессии

Принято: каждый session item ссылается на конкретную неизменяемую `ExerciseVersion`.

### ADR-007: PostgreSQL + типизированный JSONB

Принято: основные связи нормализованы, расширяемые payload хранятся в JSONB с обязательной схемой и версией.

### ADR-008: REST для первой версии

Принято: пользовательский и административный API используют REST.

### ADR-009: Telegram как первый канал, а не доменная граница

Принято: Telegram-бот и Telegram WebApp являются первыми клиентами платформы. Backend и идентичность пользователя допускают будущий браузерный клиент.

### ADR-010: Telegram-бот работает через webhook

Принято: production-интеграция с Telegram использует HTTPS webhook с проверкой секрета, дедупликацией update и передачей долгих операций в фоновые задачи.

### ADR-011: платный доступ через Entitlements

Принято: коммерческий доступ в будущем моделируется `Product`, `Purchase/Subscription`, `AccessPolicy` и `Entitlement`. Поле `is_paid` не используется как универсальный механизм доступа. Платёжная реализация отложена.

### ADR-012: сторонние API через адаптеры и outbox

Принято: внешние API изолированы портами и адаптерами; надёжные исходящие события используют transactional outbox.

### ADR-013: темы допускают связь с несколькими заданиями

Принято: `Topic` связывается с `ExamTask` через ассоциацию many-to-many. Пользовательский маршрут всегда содержит контекст текущего задания.

### ADR-014: ручное управление Mistake Queue

Принято: правильный ответ создаёт кандидата на удаление. После блока пользователь подтверждает удаление в popup и может закреплять отдельные ошибки.

### ADR-015: частичные результаты

Принято: checker возвращает балл и статус `incorrect | partial | correct`, компонентный разбор, правильные ответы и ссылки на теорию.

### ADR-016: минимальные права MVP

Принято: сложная ролевая модель не используется. Обязательное разделение ограничивается `learner` и `administrator`.

### ADR-017: технологический стек

Принято: целевой базовый стек — React + TypeScript для frontend, FastAPI для backend и PostgreSQL для основной базы.

## 27. Зафиксированные ответы и отложенные вопросы

Зафиксировано:

1. Одновременно активна одна версия курса.
2. Тема может относиться к нескольким заданиям.
3. Mistake Queue управляется через итоговый popup и ручное закрепление.
4. Частичные баллы входят в базовый контракт проверки.
5. Начальный срок неактивности сессии — 24 часа и изменяется конфигурацией.
6. Для одной комбинации `mode + scope` допускается одна активная сессия; явный выход закрывает её.
7. Автор вводит `rich_text` в безопасном Markdown.
8. В MVP используются только `learner` и `administrator`.
9. Старые пользовательские ошибки не мигрируют.
10. Целевой стек: React + TypeScript, FastAPI, PostgreSQL.
11. В MVP используется Telegram identity; браузерная аутентификация отложена.
12. Оплата не входит в текущую реализацию.
13. Будущая модель должна поддерживать продажу отдельных элементов и их комбинаций.
14. Целевая коммерческая модель допускает разовые покупки и месячные подписки.
15. Возвраты, отзыв доступа и grace period будут определены перед реализацией оплаты.

### Безопасный Markdown

`rich_text` хранится как Markdown, удобный для автора. При публикации он:

- валидируется по разрешённому подмножеству;
- преобразуется в безопасное представление или санитизированный HTML;
- не допускает произвольный HTML, script, inline event handlers и небезопасные URL;
- может кешировать результат преобразования, сохраняя исходный Markdown.

### Миграция существующего контента

После подключения рабочего репозитория и базы будет подготовлен отдельный read-only аудит данных и миграционный pipeline. Цель — сохранить полезный существующий контент, преобразовав его в новые `TheoryDocument`, `TheoryBlock`, `Exercise` и `ExerciseVersion`.

Миграция:

- не переносит пользовательские ошибки;
- не изменяет исходную базу;
- сохраняет mapping старых и новых идентификаторов;
- формирует отчёт об автоматически преобразованных и требующих ручной проверки записях;
- не публикует неоднозначно преобразованный контент автоматически.

Остаются отложенными до соответствующих этапов:

- конкретный браузерный identity provider;
- платёжный провайдер и валюты;
- правила возвратов и окончания подписки;
- точные коммерческие пакеты.
